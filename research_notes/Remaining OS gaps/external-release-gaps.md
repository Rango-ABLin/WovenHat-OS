# External and release-boundary gaps of WovenHat-OS (as of 2026-11-27)

Scope: only gaps actually documented in the repository. All links are repository-relative paths; dates are included so staleness is visible. "Software/QEMU boundary" means 1/2/4-CPU host tests, Clippy with `-D warnings`, and QEMU boots/images — explicitly *not* native hardware.

## Which release gates are explicitly marked NO-GO / BLOCKED, and what exact artifact or ceremony would close each?

### Takeaway
Every release-level decision in the repository remains NO-GO / BLOCKED. In nearly every case the repository-side tooling is *complete* and the gate is blocked only on an external ceremony or artifact: production PKCS#11 key custody, a genuinely independent build attestation, an independent security review, and named native-hardware evidence. The single clearest current statement is the top-of-file 2026-11-27 status entry: "External release gates remain explicit: native input/GPU performance and device-loss qualification; production non-exportable keys, witnessed custody, signed exact-commit artifacts, independent build/review attestation, and physical Secure Boot/TPM evidence" ([docs/stage-status.md](docs/stage-status.md), 2026-11-27, lines 18-21).

### Inferences
- The release decision is blocked by *external* dependencies, not by a missing repository script: each gate has a documented ceremony whose artifact list is precise (token evidence + witnesses; independent attestation package; signed reviewer disposition; per-device native observations + independent sign-off; power-loss logs; TPM quotes).
- The recurring phrase "tooling complete / verifier complete / adapter complete" confirms the intended classification: ceremony pending, not implementation pending, for signing custody, independent build attestation, and hardware-report policy validation.
- No single document claims that all software work is complete either: RELEASE-READINESS (2026-11-15) still says "Full current-source software acceptance and release qualification remain open," so the NO-GO is not solely attributable to external gates.

### Gaps
- No document gives the name of a selected independent organization, reviewer, lab, or PKCS#11 token serial/label; these are necessarily absent external inputs.
- No document records an actual completed Z3 authorization sign-off with operator/device-owner signatures (the 2026-11-25 template still has blank signature fields and says "Template only — not executed").
- No document quantifies a target date or owner for closing any external gate.

### Inferences
- The repository consistently treats QEMU success as a *precondition* for physical qualification, never as evidence of it; the roadmap codifies this: "Agents may not claim physical hardware certification from QEMU or virtual devices… mark the physical gate blocked, not pass it" ([docs/master-development-roadmap.md](docs/master-development-roadmap.md), lines 1828-1832).
- The existence of a "real USB" pass under QEMU passthrough and an actual native-boot attempt is the closest the project has come to hardware; both are still classified non-native and ended in Tier 3.

### Gaps
- No document lists a single native category with `passed` + `environment: native`; all 17 remain blocked, skipped, or failed.
- No physical power-loss log, torn-sector observation, volatile-controller-cache measurement, TPM quote, or physical Secure Boot handoff is referenced as retained evidence.
- No native GPU/acceleration qualification is claimed anywhere; the roadmap deliberately defers it for the first GUI release.
