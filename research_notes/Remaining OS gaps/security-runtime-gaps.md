## 1. Exact status of guest-terminated TLS (no_std provider, CryptoProvider, RNG) and what still terminates TLS

### Takeaway
Guest TLS is explicitly NOT implemented. Two prerequisites were added on 2026-11-25 (a bounded Ring-3 secure-randomness syscall and a real listen/accept ABI), and a feasibility spike showed `rustls` compiles for the kernel target without `ring`, but no `no_std` TLS provider / custom `CryptoProvider` has been built. TLS is still terminated by the controlled host mTLS proxy, which holds the client-private-key trust boundary.

### Cited Findings

- "A Ring-3 process that terminates TLS itself still needs a `no_std` TLS provider; a feasibility spike now shows `rustls` compiles for `x86_64-unknown-none` without `ring`, so that blocker is implementation effort for a custom crypto provider rather than a hard toolchain wall." — [docs/stage-status.md:282-287](docs/stage-status.md#L282-L287).
- Agent record, same date: "`rustls` itself compiles for `x86_64-unknown-none` without `ring`, so the remaining guest-TLS blocker is a custom `CryptoProvider` built from already-cached pure-Rust crates (`aes-gcm`, `sha2`, `hmac`, `p256`, `rsa`), not a hard toolchain wall. - "Ring-3 TCP listen/accept ABI - 2026-11-25": "this is the listener ABI stage only. ## 2. Trust boundary of the secure-randomness ABI (software/virtual vs certified TRNG)

### Takeaway
The `SecureRandom` ABI is a bounded, fail-closed *virtual/software-qualified* entropy interface, explicitly not a certified TRNG. It seeds only from a health-checked eight-sample RDRAND sequence mixed with boot timing; on QEMU/TCG it deliberately reports entropy unavailable and refuses all callers.

### Cited Findings
- "The generator is deterministic and is only meaningful when seeded: boot calls `seed_from_hardware()`, which requires a health-checked eight-sample RDRAND sequence mixed with boot timing. Constant, zero or repeated samples reject the seed and leave the pool unseeded, so the syscall fails closed for every caller instead of falling back to the documented non-cryptographic mixer. Output is bounded to 4096 bytes per call, keyed by domain-separated HMAC-SHA256 with a ratchet after every block, and zeroized in the syscall path." — [docs/stage-status.md:263-271](docs/stage-status.md#L263-L271).
- "Production boots under TCG log `[RNG] boot entropy: unavailable (fails closed)`: QEMU's default CPU does not expose a health-checked hardware source here, so this is the honest result, not a test failure." — [docs/stage-status.md:278-280](docs/stage-status.md#L278-L280).
- "**Trust boundary:** this is a virtual/software-qualified entropy ABI, not a certified TRNG. Physical entropy-source review and independent validation remain release gates." — [docs/stage-status.md:282-284](docs/stage-status.md#L282-L284); same in [docs/agent-coordination.md:89-97](docs/agent-coordination.md#L89-L97).
- Older kernel entropy boundary: `entropy::random_u64()` uses hardware RDRAND when available with an "explicitly non-cryptographic SplitMix64 fallback" used for TCP ISNs and ASLR; "the fallback path is not suitable for key material" — [docs/security.md:52-63](docs/security.md#L52-L63).
- Original audit of that entropy source: the fallback is "explicitly documented as *not* cryptographically secure, only better than a static constant, and unsuitable for future key-material use" — [docs/AUDIT-2026-09-04.md:55-64](docs/AUDIT-2026-09-04.md#L55-L64).
- Validation recorded: kernel Clippy (default, `secure-rng-test`), all-targets Clippy, workspace tests, full `RUN-STAGE10.7.ps1` chain, `[RNG] bounded DRBG self-test: PASSED` at 1/2/4 CPUs covering unseeded rejection, non-zero non-repeating output, oversized/zero-length rejection and post-clear fail-closed — [docs/stage-status.md:273-277](docs/stage-status.md#L273-L277).

### Inferences
- The ABI is usable as a *bounded DRBG primitive* but does not establish a hardware root of trust; its entropy quality depends on a physical RDRAND-like source that is absent in the qualification environment.
- The documented prerequisite to close the trust gap is physical entropy-source review plus independent validation, not another QEMU marker.

### Gaps
- No certified TRNG, no health-test evidence on physical hardware, and no independent entropy validation is documented.
- No documented statement of which physical CPU/platform would provide the health-checked source or how it would be certified.

## 3. Listener/accept limitations and what a full listener would need

### Takeaway
A real but deliberately minimal single-connection Ring-3 listener exists; no backlog is fabricated because smoltcp 0.14 has no public `accept()`/backlog API. A full listener would need a public accept/backlog primitive or a bounded kernel connection table, plus an actual event-driven NIC path rather than polling.

### Cited Findings
- "Syscalls `NetListen` (249) and `AsyncNetAccept` (250) are gated by `NetworkIo` like every other socket call. `UserSocket` records a `listening` flag; `socket_listen` puts a TCP socket into bounded listen state and `socket_accept_pinned` reads the accepted 4-tuple from smoltcp. smoltcp 0.14 has no public `accept()`/backlog, so this is an honest **single-connection listener**: after acceptance the socket is connected and a new socket is required for another client — no backlog is fabricated." — [docs/stage-status.md:291-297](docs/stage-status.md#L291-L297).
- "No Ring-3 pointer is retained and no caller spins"; `libwoven::network::{listen, accept}` expose the ABI; `apps/woven-remote-admin` replaced its `NET_PEER` busy loop — [docs/stage-status.md:299-304](docs/stage-status.md#L299-L304).
- Validation: WADM gate 1/2/4/8/16 CPUs with `[LISTEN]` markers, host mTLS Query/Apply/Query/Rollback/replay exchanges and `listener_abi: true`; a 16-CPU host socket timeout fixed by scaling only the harness socket budget; two environmental reruns; full serialized chain exit 0 — [docs/stage-status.md:306-314](docs/stage-status.md#L306-L314).
- "`Accept` converts one established TCP connection on the listening descriptor without allocating an unbounded connection table; the service closes and recreates the socket for another connection. Teardown does not depend on retaining network permission." — [docs/architecture-and-codebase-guide.md:3842-3846](docs/architecture-and-codebase-guide.md#L3842-L3846).
- Explicit network boundaries: "Network progress still depends on the existing polling driver, not a new hardware interrupt-driven NIC architecture. Send completion means local socket acceptance, not remote acknowledgement; closing does not promise graceful draining. Public socket descriptors remain process-local integer slots, while in-flight tokens carry generations. Generation counters remain finite. Generic completions have single-task ownership." — [docs/architecture-and-codebase-guide.md:3904-3912](docs/architecture-and-codebase-guide.md#L3904-L3912).
- Architecture lock order: "The socket worker remains CPU0-pinned. These changes do not introduce parallel smoltcp workers, per-CPU network queues or unrestricted multicore I/O services. The existing network runtime remains globally serialized. The guard does not prove every cross-subsystem lock order; broader path audits remain necessary." — [docs/architecture-and-codebase-guide.md:3880-3883](docs/architecture-and-codebase-guide.md#L3880-L3883).
- Historical note (2026-11-25, superseded): S17 virtual-model work recorded "A true Ring-3 guest listener is still **blocked**: the kernel has no listen/accept syscall, so adding one is a new ABI stage" — [docs/stage-status.md:397-404](docs/stage-status.md#L397-L404); that ABI stage then landed in the later 2026-11-25 entry at lines 289-320.
- S09 software-gap inventory (2026-10-24): "IPv6 socket lifecycle, routes/ND, profile service and full TLS certificate lifecycle remain incomplete" — [docs/release-qualification/software-gap-inventory.md:26](docs/release-qualification/software-gap-inventory.md#L26).

### Inferences
- A "full listener" would require (a) an upstream smoltcp public accept/backlog API or a bounded kernel-side pending-connection table, (b) accept of multiple clients without recreating the socket, and (c) interrupt/event-driven NIC progress and parallel/per-CPU runtime work if the global serialization is to be lifted — none is claimed.
- Even with a full listener, guest TLS termination is a separate prerequisite (question 1); the host proxy remains the TLS boundary.

### Gaps
- No documented backlog depth, multi-client lifecycle, graceful close/drain semantics, IPv6/routes/ND profile service, or full TLS certificate lifecycle.
- No documented number or owner for a future listener-hardening stage.

## 4. Font ABI limitations (per-process copies, shared mapping, cache busy flag, transmute lifetime)

### Takeaway
The accepted font design is per-process copies of a validated, read-only asset window. `transmute` and the transient cache `busy`-flag fallback were fixed on 2026-11-26, and the focused large-mapping self-test was restored the same day; the shared cross-process read-only font mapping ABI plus a written threat review remain explicitly open and unclaimed.

### Cited Findings
- "Still open: a shared cross-process read-only font mapping ABI with a written threat review. Per-process mappings remain the accepted design." — [docs/stage-status.md:89-108](docs/stage-status.md#L89-L108) ("Focused large read-only mapping gate restored - 2026-11-26 - ACCEPTED (BOUNDED SOFTWARE/QEMU)").
- That same entry documents the restored gate: original self-test was removed after reproducible TCG frame pressure in the 256 MiB memory-stress matrix, now behind its own `large-map-test` feature with a 1 GiB guest RAM budget; verifies exact bytes, read-only protection, second-map rejection, unaligned/zero-length rejection and clean unmap; data is `USER_MMAP_MAX_SIZE + 7` bytes on a fresh address space, "no large kernel stack buffer" — [docs/stage-status.md:91-105](docs/stage-status.md#L91-L105).
- "load_system_font_face no longer uses `mem::transmute` to extend a lifetime: `load_system_font_mapping` returns `&'static [u8]`, so a face parsed from it is already `'static`. It also no longer returns `None` on transient contention with its initialization `busy` flag — it waits on a bounded spin-lock acquisition, so one SMP frame cannot silently switch to bitmap text while another thread initializes the face." — [docs/stage-status.md:110-117](docs/stage-status.md#L110-L117).
- Following that entry: "Still open: per-process font copies with no shared cross-process mapping ABI, and the absent focused large-mapping kernel self-test (reproducible TCG frame pressure). Neither was claimed here." — [docs/stage-status.md:134-136](docs/stage-status.md#L134-L136). **Chronology note:** the "absent focused large-mapping self-test" was superseded later the same day by the entry at lines 89-108 that restored it under `large-map-test`.
- Address-layout collision fix (2026-11-26): "`USER_LARGE_MAP_START` and `DYNAMIC_TLS_START` were the same address"; `map_dynamic_anonymous` mapped without an unmapped-range pre-check, so a process holding the system-font window could not allocate runtime-TLS slot 0; the window was moved above the dynamic-TLS arena with compile-time disjointness assertions and the same pre-check added to `map_dynamic_anonymous` — [docs/stage-status.md:202-217](docs/stage-status.md#L202-L217). That entry's "Still open" list (per-process copies, transient `busy`-flag fallback, `'static` lifetime established by `transmute`, absent large-mapping self-test) at lines 230-233 is an *earlier* same-day snapshot, superseded by the two later entries above.
- Shell self-test font staging (2026-11-26): test-only staging of the hash/licence-validated 621,572-byte font through the existing `create_read_only_large` VFS path and adding `FileRead` to shell self-test capabilities; production `system-apps` path unchanged; full `RUN-STAGE10.7.ps1` explicitly not claimed — [docs/stage-status.md:138-174](docs/stage-status.md#L138-L174).
- Font ownership/cache boundary: `FontFallback` keeps at most eight borrowed faces and a fixed 128-entry cache; "The cache owns only validated indices and metrics, so font storage remains owned by the VFS/font loader and cannot be invalidated through cached pointers... composite or malformed outlines fail closed to the bitmap fallback" — [docs/architecture-and-codebase-guide.md:492-512](docs/architecture-and-codebase-guide.md#L492-L512).
- Stage 05 typography evidence (2026-10-25): "accepted for the bundled static-font kernel/QEMU scope. The kernel path is intentionally bounded to simple `glyf` outlines and fails closed for composites or malformed data; full UAX #9 bidi, script shaping, IME, and userspace font selection remain separate higher-level capabilities and are not claimed by this gate" — [docs/graphics/stage-05-typography-evidence.md:58-62](docs/graphics/stage-05-typography-evidence.md#L58-L62).

### Inferences
- The documented remedy for the remaining font ABI gap is a *new* shared cross-process read-only mapping ABI accompanied by a written threat review; until then per-process copies are the accepted, explicitly bounded design.
- The `transmute` and `busy`-flag items are closed by later 2026-11-26 entries; they should not be reported as current gaps without the supersession note.
- The large-mapping gate exists but is deliberately isolated (`large-map-test`, 1 GiB RAM) to avoid TCG frame pressure, so it is not part of the default memory-stress matrix.

### Gaps
- No shared cross-process mapping ABI or written threat review exists; no claim of deduplicated font memory across processes.
- No current gap remains for `transmute`, `busy`-flag fallback or the focused self-test as of the latest 2026-11-26 entries; earlier entries that list them are stale.
- No claim of complete shaping/IME/userspace font selection beyond the bounded static-font scope.

## 5. Documented unsafe-code, lock-order, owner-teardown, generation-reuse, bounded-capacity, IRQ-lock and cross-CPU concerns

### Takeaway
The rules defining a "gap" are explicit in AGENTS.md (safe Rust, minimize/document unsafe, validate userspace pointers, review owner teardown/cancellation/generation reuse/bounded capacity/lock order/local preemption/cross-CPU races, never sleep under an IRQ lock). Auditor tooling and bounded guards exist, but complete cross-domain lock-graph tracking, priority inheritance, cross-CPU race detection and broader path stress remain open.

### Cited Findings
- Project rules: "Prefer safe Rust. Document and minimize unsafe code; use assembly only where CPU architecture requires it. Do not broaden capabilities to satisfy tests." / "Validate userspace pointers and copy or pin data before asynchronous use." / "Review owner teardown, cancellation, generation reuse, bounded capacity, lock order, local preemption and cross-CPU races for every new kernel object." / "Use event-driven blocking. Never sleep or switch tasks under an IRQ lock." / "Treat test failures as defects to diagnose, not reasons to weaken assertions, disable tests, suppress warnings or increase timeouts." — [AGENTS.md:10-26](AGENTS.md#L10-L26).
- `MEMORY-SAFETY-AUDIT.md` names exactly these properties (userspace pointer validation, async data pinning, owner teardown, generation tracking, bounded capacity, lock ordering, cross-CPU races) as audit components — [docs/MEMORY-SAFETY-AUDIT.md:1-15](docs/MEMORY-SAFETY-AUDIT.md#L1-L15), [docs/MEMORY-SAFETY-AUDIT.md:107-138](docs/MEMORY-SAFETY-AUDIT.md#L107-L138). "Future Enhancements" still lists "Cross-CPU race detection - Hardware breakpoints on audit state" and "Symbolic execution - Verify audit properties statically" — [docs/MEMORY-SAFETY-AUDIT.md:247-255](docs/MEMORY-SAFETY-AUDIT.md#L247-L255).
- SMP scheduling/lock invariant: immutable CPU assignment in the original text, per-CPU cursors, `try_lock` timer handlers, "cannot schedule while their CPU holds the scheduler lock"; "`spawn_on` and `spawn_parallel` are unsafe: AP entries are restricted to atomic computation and task yield/sleep/exit primitives... The release does not claim that every legacy kernel service is safe to call concurrently from APs." — [docs/smp-lock-audit.md:1-14](docs/smp-lock-audit.md#L1-L14), [docs/smp-lock-audit.md:46-51](docs/smp-lock-audit.md#L46-L51).
- Paging/TLB lock order: "Paging paths take PAGING before the frame allocator/COW locks. No shootdown handler acquires these locks or the scheduler mutex... A timeout panics; it never silently frees a possibly cached frame." — [docs/smp-lock-audit.md:32-44](docs/smp-lock-audit.md#L32-L44).
- Stage 7 addendum: `TaskState::Switching` hand-off, userspace/legacy I/O pinned to CPU0, intended order `SCHEDULER -> PROCESS_TABLE`, and "Pager request publication uses one scheduler critical section to mark the faulting requester Blocked and make the pager Ready, preventing a lost wakeup" — [docs/smp-lock-audit.md:62-75](docs/smp-lock-audit.md#L62-L75).
- Runtime lock guard: `IrqMutex` bounded held-lock stack, monotonically increasing ranks, rejection of recursive acquisition/depth overflow/non-LIFO release; "The scheduler, process-table, paging, COW, and frame-allocator mutexes still use their established ownership wrappers and are not silently treated as covered by this worker-lock guard. Complete cross-domain lock-graph tracking and priority inheritance remain open Stage 6 work." — [docs/smp-lock-audit.md:76-88](docs/smp-lock-audit.md#L76-L88).
- `IrqMutex` vs `PreemptMutex`: "`IrqMutex` disables local maskable interrupts before taking its spin mutex... This addresses same-CPU preemption deadlock, which a plain spin mutex cannot prevent even on one CPU." `PreemptMutex` "cannot be used in an IRQ handler or around a voluntary switch"; "No task may sleep or switch while holding it" — [docs/architecture-and-codebase-guide.md:3856-3878](docs/architecture-and-codebase-guide.md#L3856-L3878).
- Production gap audit, Stage 6 row: "broader cross-layer lock stress/priority inheritance" open; follow-up: "The socket runtime and VirtIO transport now use explicit ranks 20 and 30; every current kernel `IrqMutex` construction has a declared rank. Broader lock-path stress and priority inheritance remain open." — [docs/stage1-12-production-gap-audit.md:9](docs/stage1-12-production-gap-audit.md#L9), [docs/stage1-12-production-gap-audit.md:40-46](docs/stage1-12-production-gap-audit.md#L40-L46).
- Stage 1–12 audit governing rule: "For every open item we will add implementation, focused host tests, 1/2/4 CPU QEMU tests, and an audit entry. A stage is production-complete only when every roadmap requirement has passing evidence or an explicitly accepted design." — [docs/stage1-12-production-gap-audit.md:15-17](docs/stage1-12-production-gap-audit.md#L15-L17).
- Generation/local-preemption nuance from compositor work: "The registry lock disables preemption, not interrupts. Copying a 9 MB surface must not hold interrupts off. Nothing takes the lock from interrupt context... Allocation and freeing happen outside the lock" with pre-check/re-check on create — [docs/stage-status.md:12053-12063](docs/stage-status.md#L12053-L12063).
- Security model known gaps: "File write authorization is still process-scoped (`FileWrite` capability), not per-file"; "Kernel stacks ... do not yet have guard pages"; canary is "not an unmapped virtual guard page" and kernel/double-fault stacks remain static — [docs/security.md:86-99](docs/security.md#L86-L99).
- W^X boundary and caveat: anonymous mmap hard-codes executable false; ELF parser rejects W+X; "Neither invariant currently extends to a real `mprotect`-style syscall, because none exists yet — if one is added, it must preserve the same guarantee and gain its own self-test" — [docs/security.md:40-50](docs/security.md#L40-L50).
- Capability-sandbox acceptance is explicitly bounded: Stage 9 gate covers "all twelve WovenGuard layers... This closes the existing bounded Stage 9 software/QEMU security policy on current source. Native device policy, broader adversarial stress, external security review, and collective Stage 1-19 release closure remain separate." — [docs/stage-status.md:1478-1491](docs/stage-status.md#L1478-L1491).
- S16 inventory: nine-scenario Stage 31 matrix passes; "Arbitrary in-guest fault injection, an approved compatibility target, native hardware, and independent security review remain open" — [docs/release-qualification/software-gap-inventory.md:33](docs/release-qualification/software-gap-inventory.md#L33). The Stage 31 fault-injection work is explicitly "a self-test of the seeded decision logic, not a production fault injector" — [docs/stage-status.md:501-535](docs/stage-status.md#L501-L535).
- Threat model residual risk: no claimed protection from "physical memory access, DMA by an unisolated device, speculative-execution side channels, firmware/hypervisor compromise, or power loss during an uncalibrated storage write"; production completion needs "a signed/measured boot chain, IOMMU/DMA isolation, production AEAD/key storage, unclean-shutdown testing, broader hardware drivers, and an independent red-team assessment" — [docs/threat-model.md:47-57](docs/threat-model.md#L47-L57).

### Inferences
- The documented "gaps" are mostly *scope limits* rather than known defects: auditors/guards exist and are tested, but completeness across all kernel domains is not asserted.
- New kernel objects still require a case-by-case review against the AGENTS.md checklist; passing a focused gate does not waive those reviews.
- Capability/sandbox boundaries are bounded at the WovenGuard software/QEMU layer; per-file authorization, kernel-stack guard pages, and external red-team review are the named boundaries still open.

### Gaps
- No complete cross-domain lock graph and no priority inheritance; no cross-CPU hardware race detection or symbolic audit execution.
- No per-file write authorization, no kernel-stack guard pages, no `mprotect`-style W^X invariant, no supplementary groups/credential-changing syscalls/persistent audit storage ([docs/security.md:32-38](docs/security.md#L32-L38)).
- No arbitrary in-guest fault injection into production paths; no native device policy/adversarial stress; no independent red-team result.

## 6. Secure boot and attestation boundary; capability/sandbox boundary status

Virtual Secure Boot + software TPM + signed-guest handoff is qualified only with disposable snakeoil material in WSL2. Physical TPM/Secure Boot evidence, PCR/quote-based attestation on real hardware, key revocation/rollback metadata, and production key custody remain explicit external gates; firmware-side variables are "platform integration work."

- "Virtual trust chain: OVMF Secure Boot + software TPM + signed-guest handoff qualified in disposable WSL2...
