# Four Gap Tiers Still Block WovenHat-OS

As of 2026-11-27, WovenHat-OS is still **NO-GO for release**, but the largest remaining gaps are not missing code — they are **external ceremonies that the repository already has tooling to support**. Every release decision in the records stays blocked on production non-exportable signing keys with witnessed custody, a genuinely independent build attestation and security review, named native-hardware evidence, physical power-loss qualification, and physical Secure Boot/TPM evidence ([docs/stage-status.md, 2026-11-27](docs/stage-status.md); [docs/release-qualification/RELEASE-READINESS.md, 2026-11-15](docs/release-qualification/RELEASE-READINESS.md)). Alongside those, a smaller set of **real, unimplemented software features** remains — guest-terminated TLS, a shared font mapping ABI, a full TCP listener, several desktop-shell items and a few harness limitations — while the kernel's security guarantees are explicitly bounded to virtual/software models rather than certified hardware roots ([docs/agent-coordination.md, 2026-11-25](docs/agent-coordination.md)). Stage 29 native qualification has actually **degraded from Tier 2 to Tier 3** after real boot failures, so the hardware picture is worse, not better, than the 2026-11-20 records imply ([docs/audit-stage29-hardware-qualification-2026-11-25.md, 2026-11-25](docs/audit-stage29-hardware-qualification-2026-11-25.md)). Acceptance is extensive but **dated and scoped**: almost every passing stage is labelled "ACCEPTED (BOUNDED SOFTWARE/QEMU)," never full-stage or release acceptance. Finally, the full `RUN-STAGE10.7.ps1` chain was **not run at the current head** after the 2026-11-27 personalization/signing change, and no retained current-head result proves all **11 CI jobs** green; neither is claimed here.

## External ceremonies hold every release decision at NO-GO

The single clearest current statement is the 2026-11-27 status header: "External release gates remain explicit: native input/GPU performance and device-loss qualification; production non-exportable keys, witnessed custody, signed exact-commit artifacts, independent build/review attestation, and physical Secure Boot/TPM evidence" ([docs/stage-status.md, 2026-11-27](docs/stage-status.md)). Older NO-GO records — `checkpoint.json` and `m00-baseline-ledger.md` (both 2026-10-24), `software-gap-inventory.md` S20 `BLOCKED` (2026-10-24), `RELEASE-READINESS.md` and `REMAINING-WORK.md` (2026-11-15), and `EXTERNAL-REVIEW-AND-HARDWARE.md` (2026-11-20) — have not been superseded by any promotion; the newest entry simply restates them. The decisive distinction for the user is **"tooling complete, external ceremony pending" versus "not implemented at all"**: the PKCS#11 hardware-signer adapter and repository custody boundary are complete, the independent-attestation generator and fail-closed verifier are complete, and the fail-closed hardware-qualification tooling (Z1 preflight, 108-job Z2 matrix, `qualify-hardware-report.py`) is complete ([docs/release-qualification/KEY-CUSTODY.md](docs/release-qualification/KEY-CUSTODY.md); [docs/release-qualification/INDEPENDENT-BUILD-ATTESTATION.md](docs/release-qualification/INDEPENDENT-BUILD-ATTESTATION.md); [docs/hardware-qualification-stage29-2026-11-20.md, 2026-11-20](docs/hardware-qualification-stage29-2026-11-20.md)). What is missing is the organization, the token, the reviewer and the lab, not the script.

Production signing custody is **BLOCKED PENDING HARDWARE CEREMONY**: no production token or public-key evidence is provisioned, and development signatures and test keys do not establish release custody ([docs/release-qualification/EXTERNAL-REVIEW-AND-HARDWARE.md, 2026-11-20](docs/release-qualification/EXTERNAL-REVIEW-AND-HARDWARE.md)). The token must support Ed25519 `CKM_EDDSA` signing with on-token, non-exportable private objects, PIN-controlled signing with distinct IDs for boot/app/SDK, vendor-supported encrypted backup or a second protected token, and audit records; a token that can export any private key is rejected ([docs/release-qualification/KEY-CUSTODY.md](docs/release-qualification/KEY-CUSTODY.md)). Independent build attestation is **VERIFIER COMPLETE / EXTERNAL SUBMISSION OPEN** ("VERIFIER COMPLETE" as of 2026-11-25): it explicitly cannot be satisfied by repository agents, the project owner, another local checkout, another local agent or GitHub Actions, and needs an organization legally and operationally independent of the maintainer controlling its own build host and Ed25519 key ([docs/stage-status.md, 2026-11-25](docs/stage-status.md); [docs/release-qualification/INDEPENDENT-BUILD-ATTESTATION.md](docs/release-qualification/INDEPENDENT-BUILD-ATTESTATION.md)). Independent security review is **BLOCKED** with no reviewer identity, signed scope, finding disposition or detached attestation, and the threat model additionally calls for an independent red-team assessment ([docs/release-qualification/EXTERNAL-REVIEW-AND-HARDWARE.md, 2026-11-20](docs/release-qualification/EXTERNAL-REVIEW-AND-HARDWARE.md); [docs/threat-model.md](docs/threat-model.md)).

The hardware gates are the weakest part of the picture. All **17 native categories** in `hardware-support-record.json` (2026-11-20) still read `blocked` / `PHYSICAL_NOT_TESTED`, and the 2026-11-25 native boot attempts on an HP Pavilion x360 produced **two native failures** — WovenShell remained alive without activating the display, and the `WOVENLOG` live-log path was not initialized — with **no native category holding a passed observation** ([docs/audit-stage29-hardware-qualification-2026-11-25.md, 2026-11-25](docs/audit-stage29-hardware-qualification-2026-11-25.md)). Physical power-loss/torn-media qualification is unexecuted: the Z3 Phase 3 ceremony (controlled power-loss cycles with journal-replay verification) exists only in a template, and the filesystem tracker reports no physical controller-cache, torn-sector, native-media or power-loss result ([docs/release-qualification/Z3-NATIVE-QUALIFICATION-CHECKLIST.md](docs/release-qualification/Z3-NATIVE-QUALIFICATION-CHECKLIST.md); [docs/filesystem/wovenfs-system-migration-tracker.md](docs/filesystem/wovenfs-system-migration-tracker.md)). Physical Secure Boot/TPM evidence is absent: on the Apeirova host (HP 290 G4) TPM was "not visible / not ready," Secure Boot and `bcdedit` failed closed on access denied, while the Pavilion had TPM 2.0 enabled but Secure Boot disabled and no provisioning performed; the OVMF + `swtpm` + snakeoil chain is only a "Virtual PASS" ([docs/hardware-qualification-stage29-2026-11-20.md, 2026-11-20](docs/hardware-qualification-stage29-2026-11-20.md); [docs/release-qualification/m00-baseline-ledger.md, 2026-10-24](docs/release-qualification/m00-baseline-ledger.md)).

**What closes Tier 1:**

| Gap | What would close it |
|---|---|
| Production signing custody | Witnessed PKCS#11 ceremony: three non-exportable key IDs, vendor verification of non-extractability, independent public-key read, both participants signing evidence, redundant custody or recorded recovery risk, then pinned trust roots and exact-commit artifact verification |
| Independent build attestation | Independent organization's clean-room rebuild of the exact commit with detached Ed25519 attestation; verifier returns `valid: true` plus an out-of-repository statement of key/host ownership |
| Independent security review | Named external reviewer, signed scope, finding disposition and detached attestation verified at an exact commit; independent red-team assessment |
| Stage 29 native hardware | Named lab owner; per-device evidence for all 17 categories with at least one `passed` + `environment: native` observation; repair the two native failures; separate systems for desktop/AMD/NVIDIA/SATA/Ethernet/multi-monitor; independent sign-off; update the stale `hardware-support-record.json` |
| Physical power-loss / torn media | Execute the authorized Z3 Phase 3 cycles on native media with retained journal-replay verification, controller-cache and torn-sector observations |
| Physical Secure Boot / TPM | Real-host TPM quote against a provisioned expected policy bound to the signed measurement, firmware Secure Boot variables, PCR/event logs, revocation/rollback metadata, sealed credential provisioning |

## Unimplemented software sits behind bounded QEMU success

The bounded software/QEMU boundary is genuinely broad — 1/2/4-CPU host tests, warning-denying Clippy and QEMU boots cover desktop/compositor, graphics, USB/WovenFS, wireless, audio, secure RNG, networking and install/update/rollback — but the records repeatedly forbid relabelling those results as native or release evidence ([docs/stage-status.md, 2026-11-26](docs/stage-status.md)). **Guest-terminated TLS is not implemented**: `ring` has no C sysroot for `x86_64-unknown-none`, and although a feasibility spike showed `rustls` itself compiles without `ring`, the remaining custom pure-Rust `CryptoProvider` is "a substantial dedicated stage" that was not started; TLS is still terminated by the controlled host mTLS proxy ([docs/agent-coordination.md, 2026-11-25](docs/agent-coordination.md); [docs/stage-status.md, 2026-11-25](docs/stage-status.md)). Beware a **stale record here**: the 2026-11-25 listen/accept entry says there is "no production secure-RNG syscall for Ring 3," but the later same-day entry delivers syscall 251 `SecureRandom`; only the "no `no_std` TLS provider" half remains true ([docs/stage-status.md, 2026-11-25](docs/stage-status.md)). The listener itself is deliberately **single-connection** because smoltcp 0.14 has no public `accept()`/backlog, no backlog is fabricated, network progress still polls rather than using an interrupt-driven NIC, and the socket worker remains CPU0-pinned with globally serialized I/O ([docs/architecture-and-codebase-guide.md](docs/architecture-and-codebase-guide.md)).

The desktop shell has a cluster of unclaimed items with shared root causes. **WSIZ client reflow on maximize is NOT DONE** and window shadows are temporarily disabled because both hit a reproducible `present_region_blended` stall on slow 1-CPU QEMU; **cross-boot pin/auto-hide persistence**, an **in-shell taskbar settings editor**, and **fullscreen/maximize visual polish** remain unclaimed because the shell holds only `FileRead` and no write path; **Alt+Tab is ABI-blocked** because `libwoven::Key` has no modifier-key concept; and taskbar layout is verified only for `left`+`large`, not every theme/density combination ([docs/stage-status.md, 2026-11-23/24](docs/stage-status.md)). Do **not** report auto-hide, minimize/restore, frame-only maximize, taskbar alignment/icon-size controls or Battery saver/Night light as open — those were implemented or replaced in 2026-11-24 records. The only input flake still open is the **pointer-step flake** ("mouse click did not change the client framebuffer"); the `keyboard_refresh` flake was root-caused on 2026-11-23 as a harness oracle defect and closed ([docs/stage-status.md, 2026-11-23](docs/stage-status.md)). At the app level, **full editor GUI pointer behavior** is not accepted (relative-click fails identically on the pre-change baseline), the editor overwrite-tail limit is an **accepted ABI limitation** (no truncate primitive), and the WovenFiles mutation CLI runs under `/tmp` because the disposable FAT32 image has no provisioned `/mnt` ([docs/release-qualification/APPLICATION-INTEGRATION-REPORT.md, 2026-11-25](docs/release-qualification/APPLICATION-INTEGRATION-REPORT.md)). **Live theme propagation, however, closed on 2026-11-27** — the shell's periodic settings observer now applies theme and reduced-motion changes live without write authority — so the 2026-11-15/25 wording is stale ([docs/stage-status.md, 2026-11-27](docs/stage-status.md)).

Two more boundaries deserve emphasis. The shared cross-process read-only font mapping ABI with a written threat review remains open, **but the `transmute`, transient `busy`-flag and missing large-mapping self-test items were all closed on 2026-11-26** (the self-test restored behind `large-map-test` with 1 GiB guest RAM), so earlier same-day "still open" lists are stale ([docs/stage-status.md, 2026-11-26](docs/stage-status.md)). And the S00–S20 inventory (2026-10-24, header stale but table content updated through 2026-11-26) still records IPv6 socket lifecycle/routes/ND/profile service and full TLS certificate lifecycle (S09), generic driver crash supervision/hotplug breadth/power transitions (S08), disk-full logging and privilege-separated service qualification (S07), and only a bounded freestanding C ABI (S02/S03) as incomplete; several PARTIAL virtual rows (S10/S12/S13/S17) were closed in November but cannot bypass sequential prerequisite order ([docs/release-qualification/software-gap-inventory.md, 2026-10-24](docs/release-qualification/software-gap-inventory.md); [docs/stage-status.md, 2026-11-25](docs/stage-status.md)). Native GPU acceleration is deliberately deferred by the roadmap for the first GUI release, and e1000 MSI/MSI-X, interrupt-driven dataplane, real link-state handling and offloads remain unimplemented ([docs/PHASE-C-NATIVE-HARDWARE-RECONCILIATION.md, 2026-11-23/24](docs/PHASE-C-NATIVE-HARDWARE-RECONCILIATION.md)).

**What closes Tier 2:**

| Gap | What would close it |
|---|---|
| Guest-terminated TLS | Dedicated stage implementing a custom pure-Rust `CryptoProvider` (`aes-gcm`, `sha2`, `hmac`, `p256`, `rsa`) for `rustls` on `x86_64-unknown-none`, with its own guest-side certificate/credential boundary |
| Full TCP listener | Upstream public accept/backlog API or bounded kernel pending-connection table; multi-client lifecycle; interrupt/event-driven NIC progress |

## Trust boundaries end at virtual and software models

The security/runtime gaps are mostly **scope limits rather than known defects**: auditors, guards and fail-closed paths exist and are tested, but completeness across all kernel domains is not asserted ([docs/MEMORY-SAFETY-AUDIT.md](docs/MEMORY-SAFETY-AUDIT.md)). Syscall 251 is a bounded HMAC-SHA256 DRBG seeded only from a health-checked eight-sample RDRAND sequence mixed with boot timing, capped at 4096 bytes per call and failing closed for every caller when unseeded; TCG production boots honestly log `[RNG] boot entropy: unavailable (fails closed)`, and the architecture guide calls it "a virtual/software-qualified entropy ABI, not a certified TRNG" ([docs/stage-status.md, 2026-11-25](docs/stage-status.md)). Physical entropy-source review and independent validation are the named closure, not another QEMU marker. Similarly, a **PCR read is not an attestation** and the TPM CRB probe output is wiped and is not a credential root; the Stage 24.52 broker is implemented but no broker is installed without physical provisioning inputs, and Stages 24.57/24.58 still need a live TPM to qualify the success branch ([docs/architecture-and-codebase-guide.md](docs/architecture-and-codebase-guide.md)). Firmware UEFI Secure Boot variables, TPM PCR/event logs, key revocation and rollback metadata are explicitly "platform integration work," and key rotation is a coordinated OS release transition rather than an in-place runtime secret swap ([docs/security.md](docs/security.md); [docs/release-qualification/KEY-CUSTODY.md](docs/release-qualification/KEY-CUSTODY.md)).

The threat model makes no claim of protection from **physical memory access, DMA by an unisolated device, speculative-execution side channels, firmware/hypervisor compromise, or power loss during an uncalibrated storage write**, and names signed/measured boot, IOMMU/DMA isolation, production AEAD/key storage, unclean-shutdown testing, broader drivers and an independent red-team assessment as production completion work ([docs/threat-model.md](docs/threat-model.md)). Named hardening gaps include file write authorization that is process-scoped (`FileWrite`) rather than per-file, kernel stacks without guard pages, a W^X invariant hard-coded in anonymous `mmap` and the ELF parser but with no `mprotect`-style syscall to preserve it, and missing supplementary groups, credential-changing syscalls and persistent audit storage ([docs/security.md](docs/security.md)). On the concurrency side, complete cross-domain lock-graph tracking and priority inheritance remain open; cross-CPU hardware race detection and symbolic execution sit in "Future Enhancements"; `spawn_on`/`spawn_parallel` are unsafe with APs restricted to atomic computation and yield/sleep/exit; and broader cross-layer lock-path stress is explicitly open even though every current kernel `IrqMutex` now has a declared rank ([docs/smp-lock-audit.md](docs/smp-lock-audit.md); [docs/stage1-12-production-gap-audit.md](docs/stage1-12-production-gap-audit.md)). Finally, the Stage 9 WovenGuard twelve-layer chain is closed only for the bounded software/QEMU policy, and Stage 31 fault injection is "a self-test of the seeded decision logic, not a production fault injector" ([docs/stage-status.md, 2026-11-20/25](docs/stage-status.md)).

**What closes Tier 3:**

| Gap | What would close it |
|---|---|
| Entropy trust boundary | Physical entropy-source review, health-test evidence on hardware and independent validation; a certified TRNG claim |
| TPM/attestation | Live TPM success branch, provisioned expected policy or verified quote bound to the signed boot measurement, sealed credentials, PCR/event-log evidence |
| Threat-model residuals | IOMMU/DMA isolation, signed/measured boot chain, production AEAD/key storage, unclean-shutdown testing, independent red team |
| Hardening | Per-file write authorization, kernel-stack guard pages, `mprotect`-style W^X with its own self-test, supplementary groups/credential syscalls/persistent audit storage |
| Concurrency | Complete cross-domain lock graph, priority inheritance, cross-CPU race detection, broader lock-path stress |
| Fault injection | Production fault injector and native device policy/adversarial stress, not seeded self-tests |

The roadmap defines a sequential Stage 10.7 → 36 program across 24 phases and forbids promoting QEMU evidence into hardware or trust claims; AGENTS.md adds per-call-site feature guards, stage-feature Clippy rules and single-chain execution, and states that "source integration or a focused pass is not full stage acceptance" ([docs/master-development-roadmap.md](docs/master-development-roadmap.md); [AGENTS.md](AGENTS.md)). The **Stage 1–19 closure ledger is BLOCKED / NOT PRODUCTION-READY**, with the rule that "missing evidence is blocked, not inferred from an older green run" ([docs/stage1-19-closure-gate.md](docs/stage1-19-closure-gate.md)). No acceptance record was found for Stages 33 (Alpha), 34 (Beta), 35 (RC) or 36 (1.0), none for Stage 25 power beyond design text, Stage 32 is an "ACCEPTED BOUNDARY" explicitly not full Stage 32 acceptance, full Stage 20 is not claimed, and Stage 29 is Tier 3 — so these should be reported as "no full-stage acceptance record," not inferred green. Conversely, Stages 1–24 have many bounded ACCEPTED/CLOSED/VERIFIED records whose scope limit (software/QEMU, focused, exact-source, virtual model) *is* the acceptance boundary itself.

Two evidence gaps must be stated negatively. The full mandated chain, `RUN-STAGE10.7.ps1`, is reported exit 0 in retained records through 2026-11-26, but **two 2026-11-26 increments explicitly did not run it** because other owners held the shared fixed output paths, and **the 2026-11-27 personalization/signing entry claims only focused gates** — there is no record of a fresh full-chain run at current head ([docs/stage-status.md, 2026-11-26/27](docs/stage-status.md)). Stale or superseded records are the main trap for anyone reading the repository cold. The font `busy`/`transmute`/large-map items closed on **2026-11-26** and live theme propagation closed on **2026-11-27**; the **2026-11-25** listen/accept entry is stale on secure RNG; the S-slice inventory's PARTIAL rows were partly superseded by **2026-11-25** virtual models; and the **Stage 29 Tier 2 → Tier 3** change is a documented downgrade, not an unresolved contradiction — attempt 2 explicitly supersedes the provisional Tier 2 classification with fail-closed Tier 3 native failures ([docs/audit-native-hardware-boot-attempt-2-2026-11-25.md, 2026-11-25](docs/audit-native-hardware-boot-attempt-2-2026-11-25.md)). There is no machine-readable current-status index, no single consolidated ledger reconciling these dates, no single index mapping preserved failures to dispositions, a referenced `docs/audit-physical-wovenfs-2026-11-25.md` could not be located, and a 2026-11-26 record still reports pre-existing global `cargo fmt` drift ([docs/agent-coordination.md, 2026-11-26](docs/agent-coordination.md)).

## Conclusion

The bottleneck has shifted: most Tier 1 gaps cannot be closed by another commit, because the verifiers, adapters and qualification tooling already exist and explicitly reject self-attestation. That makes the organizational acts — a token ceremony, an independent organization, a named reviewer, a named lab — the critical path, while the two cheap evidence actions (a current-head full chain and an all-green 11-job CI run) are the only "gaps" a single agent can close immediately and must not be reported as already green. The recurring "ACCEPTED (BOUNDED SOFTWARE/QEMU)" label is doing real epistemic work, and the genuinely dangerous condition is not the open gates themselves but the stale records that make closed font/RNG/theme items look open and the Tier 2 hardware classification look current when Tier 3 is. Prioritization should therefore follow: close the cheap evidence gaps first, pursue external attestations in parallel, and treat the unimplemented software items as bounded stages with their own gates rather than patch work.
